01

In short

  • Where it starts: the Rust telnet honeypot recorded 839 bot logins and the steps they took afterwards, from default passwords to malware downloads. Its report ends with what defenders should do. This project does it.
  • What I built: 17 Sigma alert rules, one or more for every step of that playbook; Google Cloud firewall rules in Terraform that only let approved addresses reach admin ports and only let IoT devices reach the servers they need; and an internal decoy NAS, running the honeypot's own fake shell, that no real person or system ever uses.
  • Why it holds together: a single file, allowlist.yaml, lists who is allowed in, where IoT devices may go and where the decoy lives. Terraform builds the firewall from it, and a script writes the same addresses into the alert rules, so the firewall and the alerts can't drift apart.
02

Three layers

  1. Bots stop at the edge. Admin ports (SSH, RDP, VNC and device web pages) only answer the VPN, static office addresses and Google's Identity-Aware Proxy. Telnet, the door every bot on the honeypot came through, is closed to everyone by default, the allowlist included.
  2. Approved people still get in. One door, preferably the VPN. Losing a laptop means revoking one VPN account, not editing the firewall.
  3. IoT devices can't call out. Every dropper the honeypot saw fetched its payload from a raw IP address on the internet. IoT devices may only reach the few servers they need, so that download fails, and the blocked attempt is an alert.
  4. Anything that touches the decoy is an alert. The NAS decoy sits inside the network with an ordinary server name. Nothing legitimate uses it, so a connection means someone inside is exploring: a compromised device, a bot past the edge, or a person who shouldn't be there.
03

Every playbook step, as an alert

The honeypot recorded the same playbook again and again. Each step became at least one rule, written in Sigma so it converts to Splunk, Sentinel, Elastic and other SIEMs. Rules that read firewall logs work everywhere; the rest need process or login logs from the device itself, which many IoT devices can't provide.

04

The trap

  • It's the honeypot, moved inside. The decoy runs the same Rust fake shell, with the same safety design: every reply is fixed text, and nothing a visitor sends is ever run. What changes is where it sits and what it's called. It has no public IP, an ordinary NAS hostname, and a bland network tag.
  • Twelve NAS ports, one that answers. Only telnet answers, with the fake shell. FTP, SMB, AFP, NFS, rsync and the usual NAS admin pages have nothing behind them, but the cloud firewall still logs every attempt to reach them, and that's all an alert needs.
  • It can't become a foothold. The decoy can't start a connection: outbound traffic is denied by the cloud firewall and again by nftables on the host. If it ever tries, that's its own critical alert, and the answer is to shut it down.

Why this is worth having. The allowlist and the IoT rules stop bots at the door. The decoy catches what got past it. Because nothing legitimate ever connects to it, its alerts have almost no false positives, which is rare for detection inside a network. The one exception is an approved vulnerability scanner, and the allowlist file has a place to exclude those.

05

What's tested, and what isn't

  • Tested on every push. GitHub Actions checks every rule, including its ATT&CK tags, and fails the build on any issue. It then converts all 17 rules to Splunk searches and validates the Terraform. While building it, that check caught two real problems: tags that a newer ATT&CK release had renamed, and a correlation rule that was silently swallowing two of the rules it was built from.
  • Not tested yet. It hasn't been deployed to a real company network. The rules have been converted, not run against live logs, and the Terraform has been validated, not applied. The repo ships with placeholder addresses, and its README lists the checks to run once the real ones are filled in.
